# 0038. A confirmed email is required to sign in whenever the server sends email

Accounts made with email and password must confirm their email before they can sign in, whenever email sending is configured. Magic link sign in, changing the email address, and a "password changed" notice ship with it, and account emails are sent through a retried job.

Status: Accepted, 2026-10-22

- ADR status: Accepted
- Date: 2026-10-22
- Deciders: coordinator as product owner (founder decision, 2026-10-22, and the default for accounts created earlier)
- Related: [0004](0004-better-auth.md), [../architecture/authorization.md](../architecture/authorization.md), [../operations/operator-guide.md](../operations/operator-guide.md#email-and-sign-in), [../product/user-journeys.md](../product/user-journeys.md) journey 1

## Context

Until now anyone could sign up with someone else's address and sign in at once, and the confirmation link signed in whoever clicked it (`autoSignInAfterVerification`). That allows account pre hijacking: an attacker creates the account first, the real owner later confirms or starts using it, and the attacker still knows the password (Better Auth review, 2026-10-21).

The platform review also asked for a page that says what happened after a confirmation link, a confirmed email before connecting Stripe, magic link sign in (REQ-ID-002), and a way to change the email address. The email review (18) found that account and invite emails were dropped when the mail server was down for a minute, that the confirmation email did not say how long the link works, that the "someone tried to sign up" email sent people to a second form, and that there was no "password changed" email.

A self-hosted server without a mail server cannot deliver a confirmation link, so requiring one there would lock everyone out.

## Decision

1. **When verification is required.** `requireEmailVerification` is on exactly when `EMAIL_DRIVER=smtp`, which is always the case on Cloud. With `EMAIL_DRIVER=log` (no mail server) it stays off, sign up signs people in as before, and the operator guide says why. `emailSendingConfigured()` in `@cohory/auth` is the one place that decides it.
2. **Sign in.** An unconfirmed account answers a correct password with 403 `EMAIL_NOT_VERIFIED`; a wrong password still gets the generic 401, so the state of an account is not revealed. The sign in form then says "Confirm your email first" and offers "Send a new link". Better Auth's `sendOnSignIn` stays off, so repeated attempts do not send repeated emails.
3. **The link never signs the clicker in.** `autoSignInAfterVerification` is off. Every confirmation link lands on `/verified?next=…`, which says "Email confirmed" with Continue (signed in) or Sign in (signed out), or, for an expired or used link, "This link has expired" with a form to send a new one. The auth hooks rewrite `callbackURL` on sign up, resend, and change email, so every caller gets this page. The link works for 1 hour, and the email says so.
4. **Pre hijacking is closed** by these paths: an account someone else created for your address stays unusable until the mailbox is proven; a magic link for an unconfirmed account removes every password and session it had (Better Auth's `revokeUnprovenAccountAccess`); and a password reset now also confirms the email, because the reset link proved the mailbox, so the owner replaces the attacker's password and signs in. A confirmation link proves the mailbox but not who chose the password, so when an account with a password is confirmed (`emailVerification.beforeEmailVerification`), a `verifications` row `unproven-password:<user id>` marks that password as unproven (no schema change; it expires after a year). The next magic link sign in for that account (`databaseHooks.session.create.after` on `/magic-link/verify`) deletes the password, signs out every other session, revokes API credentials, removes the marker, and emails "We removed a password you did not set. Set a new one from Security." Only a password reset clears the marker; changing the password on Security does not, because whoever chose the first password could also change it.

   What remains: an owner who clicks a confirmation link they did not ask for and never signs in afterwards leaves the other person with a working password. The mitigations are the email copy ("If you did not ask for this, you can ignore this email"), the click not signing anyone in, and the reset path, which ends that access at any time.
5. **Magic link.** Better Auth's magic link plugin, offered as "Email me a sign in link" on the sign in form when email sending is configured (the endpoint answers 404 otherwise). Links work for 15 minutes and once, tokens are stored hashed, and links are sent only to addresses that have an account; any other address gets the same answer and no email. It does not create accounts. A failed link returns to sign in with "This sign in link has expired or was already used."
6. **Change email.** Account, Security has an Email address section (when email sending is configured). The current address approves first: Better Auth's `sendChangeEmailConfirmation` sends "Approve your new Cohory email address" to it, and only that click sends "Confirm your new email address" to the new one. The account moves after the new address is confirmed, and then every other session is signed out and API credentials are revoked, as after a password change. This runs in an after hook on `/verify-email` instead of `afterEmailVerification`, because only the hook knows which session to keep. Better Auth skips the approval for an unconfirmed account, so the change is refused (403 `EMAIL_NOT_VERIFIED`) until the current address is confirmed; only sessions from before this decision can be in that state. A new address that already has an account gets the same answer and no email.
7. **Password changed.** A successful change on Security or a password reset sends "Your Cohory password was changed" with the time and the browser and system read from the user agent, and a link to reset it.
8. **Rate limits.** Resend, magic link, and change email requests are limited per address (the `passwordReset` rule, 5 per 10 minutes) and per client address (the `signIn` rule, 10 per minute), on top of Better Auth's own limits.
9. **Retried delivery.** Account emails (confirmation, reset, existing account, magic link, change email, password changed, password removed) and the free access and "membership has moved" invitations go through a pg-boss job `email.send` with `{ template, to, data }`. The worker renders the template and logs only the job id, the template, and an error code; the recipient and the link never reach logs or the job error. Tests and integrations that pass only a mailer keep sending at once.

   Jobs hold working links in plain text. They are not encrypted, because the database is already a trust boundary for sessions and reset tokens. Instead no job outlives the shortest link in it: the queue keeps waiting jobs (`retentionSeconds`) and finished jobs (`deleteAfterSeconds`) for at most 15 minutes, the life of a magic link, and retries (4, with backoff from 30 seconds up to 4 minutes) end within about 8 minutes. A confirmation email that could not be sent within 15 minutes is dropped, and the person asks for a new link. `createQueue` leaves an existing queue unchanged, so the web app and the worker read the queue's options and call `updateQueue` when they differ (`ensureEmailSendQueue`).

   Accepted: a retry can send the same email twice when the mail server accepted it but the job still failed (for example a timeout after delivery). Both copies hold the same link. A pg-boss `singletonKey` would not prevent this on a standard queue, since it only removes duplicates on queues with a singleton policy, so none is set.
10. **Accounts created before this.** Existing sessions keep working. Owners of unconfirmed accounts can confirm through "Send a new link", a magic link, or a password reset. To spare them that, the operator runs `pnpm accounts mark-verified --created-before <time>` (in Docker, `docker compose exec worker node apps/worker/dist/accounts-cli.js mark-verified --created-before <time>`) once, with the time email sending was turned on. By default it only prints how many unconfirmed accounts were created before then, with the earliest and latest creation time; with `--yes` it marks them as confirmed and writes an `account.email_marked_verified` entry to each account's audit log. It is a command, not a migration, because the right time differs per server and only the operator knows it. Imported people with no password (archive and members imports) are unconfirmed and confirm through "Forgot password" as before, which now also confirms their email.
11. **Connecting payments.** When email sending is configured, connecting Stripe or another provider needs a confirmed email. The Payments service enforces it (`connectStripe`, `connectOwnKeys`, `connectProvider` throw `EmailNotConfirmedError`, code `email_not_confirmed`), so the web actions, the REST routes (`POST …/payments/connect` and `…/own-keys`, 403), and the MCP tools built from them all refuse it. Manage, Payments also shows "Confirm your email first" with "Send a new link" in place of the connect controls.
12. **Logs.** Better Auth logs at `warn` and above through a logger that replaces email addresses with `[email]`, so messages such as "Sign-up attempt for existing email" never carry an address.
13. **Timing.** The magic link request looks the address up before it sends, so an address with an account takes a little longer to answer than one without. Accepted: the difference is one indexed lookup and the queue insert, the answer is the same, and the endpoint is rate limited per address and per client.
14. **Ids.** Better Auth now uses `generateId: "uuid"`. The schema's `$defaultFn` still makes UUIDv7 ids, and Better Auth shapes the ids it derives itself (such as the single use reservation of the magic link cleanup) as uuids, which the `uuid` columns require.

## Consequences

- People on a server with a mail server confirm their email before their first sign in. The sign up form already said "Check your email"; it now says the link works for 1 hour.
- A server set to `EMAIL_DRIVER=smtp` without a working mail server cannot onboard new people. The operator guide tells operators to use `EMAIL_DRIVER=log` until mail works.
- The end to end suite runs with `EMAIL_DRIVER=log`, so its sign up helpers are unchanged; the required flow is covered by `packages/auth/src/verification.integration.test.ts` and `takeover.integration.test.ts`.
- Every password chosen at sign up is unproven until a reset, because the server cannot tell who chose it. A person who signed up with a password, confirmed, and later signs in with a magic link loses that password and gets the "We removed a password you did not set" email, even when they chose it. They set a new one from Security or use magic links.
- The worker depends on `@cohory/auth` through the `@cohory/auth/accounts` entry only, which imports no Better Auth code. `@cohory/email` depends on `pg-boss`.

## Alternatives considered

- **Keep sign in open and revoke sessions and force a reset when an unconfirmed account is confirmed** (the review's first option). It keeps the attacker's session alive until the click and needs state Better Auth does not keep. Rejected in favor of decision 8.
- **Mark existing accounts verified in a SQL migration.** The cutoff differs per server and migrations cannot know when an operator turned on email. Rejected.
- **Let the magic link create accounts.** Sign up would then skip the name and the consent line. Left for later.
