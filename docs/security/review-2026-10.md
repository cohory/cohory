# Internal security review, October 2026

Checklist, evidence, findings, and what is left for an external review of cohory MVP 0.1.0.

Status: Draft, 2026-10-18

This review was done on the code at MVP 0.1.0 by reading the sources, running the test suites, building the app, and checking live responses. It is an internal review. An external review is a human procurement step and stays pending (section 5). The threat model is in [threat-model](threat-model.md).

Severity scale: critical (tenant isolation, payment integrity, or account takeover with no precondition), high (same classes with a precondition, or a missing baseline control), medium (weakens a control, needs another weakness to exploit), low (hardening).

## 2. Findings

| Id | Severity | Area | State | Location |
|----|----------|------|-------|----------|
| F-01 | High | Headers and transport | Fixed | `apps/web/next.config.ts` sent no security headers. Added `apps/web/lib/security-headers.ts` with nosniff, frame denial, referrer policy, permissions policy, HSTS, and `frame-ancestors 'none'`. Verified on the built app |
| F-02 | Medium | Rate limits | Fixed | `packages/rate-limit/src/limiter.ts` `clientIp` took the first `X-Forwarded-For` entry, which a client can set, so auth limits were bypassable behind proxies that append. Now takes the last entry. Docs updated in [self-hosting](../self-hosting.md) |
| F-03 | Medium | Deployment | Open, owned by the launch stream | `docker-compose.yml` line 54 publishes the web port on all interfaces by default (`${APP_PORT:-3000}:3000`). With a proxy on the same host the app is reachable without TLS and without the proxy's forwarded headers. Recommendation: default to `127.0.0.1:${APP_PORT:-3000}:3000` and document the override for remote proxies |
| F-04 | Medium | Content Security Policy | Fixed (Step 16) | `apps/web/proxy.ts` generates a 128 bit nonce per request and sends an enforced policy: `script-src 'self' 'nonce-...' 'strict-dynamic'`, `connect-src 'self'`, `frame-src` for YouTube, Vimeo, Loom, `img-src 'self' data: blob:`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`. The root layout renders per request so Next.js can put the nonce on its scripts. The policy went straight to enforcement instead of report only: the end to end suite fails on any violation in the console and passed every journey, Stripe Checkout redirects included. No lesson image hosts are configured by default, so `img-src` needs none |
| F-05 | Medium | Authentication | Fixed (Step 16) | Sign up answered 422 for an address that already had an account. `autoSignIn` is now off: sign up answers 200 with `token: null` for every address, emails the owner of an existing address (`onExistingUserSignUp`), and the web form signs in with the password just entered or shows "Check your email". The verification link signs the person in (`autoSignInAfterVerification`). Residual: a sign in after sign up with a guessed password still differs between a new and an existing account; both endpoints stay rate limited |
| L-01 | Low | Database | Accepted | The application role holds `CREATE` on the database for the pg-boss schema. A compromised app role could create schemas but not read tenant rows past RLS |
| L-02 | Low | Logging | Fixed ([0044](../decisions/0044-composition-roots-and-shared-infrastructure.md)) | The web process logged through `console` without a redaction layer. Nothing sensitive was logged (checked by grep). Every process now logs through `@cohory/infra/logger`, which redacts the same keys, and an ESLint `no-console` rule keeps the sources on it |
| D-01 | High (advisory), none (exposure) | Dependencies | Open | `braces` through the Next lint plugin. Not shipped |
| D-02 | Moderate (advisory), none (exposure) | Dependencies | Open | `esbuild` through `drizzle-kit`. Not shipped |
| P-01 | High | Payments | Open, for the payments stream | No handler for `account.application.deauthorized` and no app side disconnect that clears `application_fee_percent` on existing subscriptions (`packages/payments/src/service/webhooks.ts` lines 302 to 323 list the handled events; `packages/payments/src/service/connection.ts` sets `disconnected` only when own keys are replaced, line 184). [payments](../architecture/payments.md) section 10.3 describes the required job. Until it exists, a creator who disconnects in the Stripe dashboard keeps paying the fee, which AGENTS.md section 7 treats as high risk |
| A-01 | Medium | Agents | Fixed (security audit run 1) | The approval summary read for a proposal could resolve outside the token's community. Summary reads are now encoded and contained, and the path parameters they use are validated by shape |
| A-02 | Medium | Agents | Fixed (security audit run 1) | An approval request stored the raw body and showed a shortened diff, so approvers could miss a change that ran. The stored input and the diff now come from the normalized request, and a diff that does not fit is refused |
| A-03 | Low | Authentication | Fixed (security audit run 1) | `packages/auth/src/redirects.ts` checked the `next` path before resolving dot segments, so the resolved path could point at another site. It now checks the resolved path as well |
| A-04 | Low | Rate limits | Fixed (security audit run 1) | `clientIp` keyed limits on the exact address string, so each address in an IPv6 /64 and each written form of one address had its own budget. Keys are now canonical, IPv4 mapped addresses use the IPv4 form, and IPv6 is grouped by /64 |
| A-05 | Medium | Agents | Fixed (security audit run 1) | Disconnecting another person's OAuth grant treated every community wide agent as owned by the caller, whatever the role. It now uses the agent manage check, which counts community wide agents as owned only for owners and admins |
| A-06 | Medium | Agents | Fixed (security audit run 1) | The owner, and admins for community wide agents, could widen another person's agent and issue a token that acted as that person. Only the person an agent acts for now issues its tokens or widens it, managers may only narrow, pause, or revoke, and tokens issued for someone else are refused |
| A-07 | Medium | Calendar | Fixed (security audit run 1) | The reminder job claimed every going RSVP without checking membership, so removed or banned members kept getting reminders with the event location. The claim and the going count now read only RSVPs of active members; RSVPs are kept and ignored rather than deleted |
| A-08 | Medium | Communities | Fixed (security audit run 1) | Leaving kept the staff role on the membership row and every reactivation path restored it, so a departed admin or moderator got the role back by joining again. Leaving now resets the role, reactivation keeps a role only on an already active row, and personal tokens from before leaving are revoked |
| A-09 | Medium | Payments | Fixed (security audit run 1) | The email ban was checked only on free joins, requests, and invites. Checkout, paid rejoin, subscription activation, and the access resolver now refuse an account whose email is banned in the community |
| A-10 | Medium | Payments | Fixed (security audit run 1) | The membership change for a subscription event ran after the subscription transaction committed and was decided from the stored previous state, so a failure between the two left a revoked subscription with an active membership that retries never fixed. The change now runs in the same transaction under a membership row lock and is decided from the current state |
| A-11 | Low | API tokens | Fixed (security audit run 1) | Search checked only `posts:read`, so a token without `members:read` or `courses:read` still got member and lesson hits, and profile reads returned recent posts and comments without their read scopes. Each result group now follows its own scope through a scope check the route passes to the service |
| A-12 | Medium | Authentication | Fixed (security audit run 1) | A password reset or change revoked sessions only, so personal tokens, agent tokens, and OAuth grants kept working for whoever held them. Both now revoke every bearer credential of the person through the agents service |
| A-13 | Medium | Payments | Fixed (security audit run 1) | Subscriber linking matched Stripe customer emails, which the manager controls, against every account on the instance, showing account existence and adding the person without consent. On Cloud only members are matched and other addresses become invites the person claims |
| A-14 | Medium | Migration | Fixed (security audit run 1) | The members CSV preview labeled each address by whether it had an account anywhere on the instance, and add mode reused accounts whose email was never confirmed. On Cloud the preview no longer tells them apart; on the Community Edition add mode invites unconfirmed accounts instead |
| A-15 | High | Migration | Fixed (security audit run 1) | Archive import and platform importers linked archive people to existing accounts by email, including unconfirmed ones, and restored memberships and content in their name. Now only the owner's own account (and on the Community Edition confirmed accounts) is linked; others become unlinked placeholders |
| A-16 | Medium | Payments | Fixed (security audit run 1) | Comped access by email or user id added any existing account to the community at once and answered differently for unknown addresses. On Cloud an email grant is an offer the person accepts, with the same answer for every address, and a user id must belong to a member |
| A-17 | Medium | Payments | Fixed (security audit run 1 follow up) | Subscriber linking and invite claims did not check bans recorded by email, so a new account with a banned address could be linked, added, or claim an invite. Discovery now marks such addresses banned, linking and inviting refuse them, and claiming refuses an account whose email is banned |

## 5. Deferred to the external review

These need an outside party, test accounts on Stripe, or time the internal review did not have.

1. Black box testing of tenant isolation across every `/api/v1` route with two communities and the generated route test described in [multi-tenancy](../architecture/multi-tenancy.md) section 3.5 item 1, which does not exist yet.
2. Session handling under a real reverse proxy with TLS: cookie scope, HSTS behavior, and forwarded headers.
3. Stripe Connect flows in a sandbox: webhook replay, out of order delivery at scale, disconnect (P-01), refunds and disputes.
4. Upload handling with fuzzed files (polyglots, decompression bombs in ZIP, PDF with scripts) beyond the magic byte checks.
5. Dependency and container image scanning in CI.
6. The Content Security Policy (F-04), enforced since Step 16, against browsers other than Chromium.
7. Rate limit behavior with several web processes, where counters are per process.

## Decisions and open questions

- **Recommendation:** fix P-01 before any Cloud Edition deployment, since it changes what creators are charged.
- **Recommendation:** adopt F-03 in the Compose defaults in the launch stream.
- **Decision (Step 10, N1):** F-05 stays open and is deferred. Better Auth 1.7.10 returns the generic response for an existing address only when `autoSignIn` is false or `requireEmailVerification` is true (`sign-up.mjs` lines 155 to 204), and then it signs nobody in, new members included. Closing it means: set `autoSignIn: false`, show "Check your email" after sign up, sign in after the verification link (`autoSignInAfterVerification`), and email the existing owner through `onExistingUserSignUp`. That changes journeys 1 and 3 and every end to end fixture that relies on the session cookie from sign up (`apps/e2e/support/fixtures.ts`), which another unit owns in this step. Rate limits on `/sign-up/email` stay the mitigation until the product owner agrees to the new sign up flow.
- **Decision (Step 16):** F-05 is closed as the Step 10 note described. The web sign up form signs in right after sign up with the password just entered, so journeys 1 and 3 keep their shape; the end to end fixtures sign in after the API sign up.
- **Open question** (security audit run 1, A-01): an approval summary quotes member names and roles and course or event titles even when the agent holds the write scope but not the matching read scope (`members:read`, `courses:read`, `events:read`). Leaving them out for such agents would also take them out of what approvers see, so the change waits for a product decision on separate agent and approver summaries.
- **Open question:** whether to run `pnpm audit --prod` in CI as a warning or a failure.
